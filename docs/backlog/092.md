# 092 · Adaptador Codex persistente via `codex app-server`

## Objetivo

Migra a integração do provedor Codex de execuções efêmeras por turno (`codex exec --json`) para uma sessão persistente sobre **`codex app-server`** (JSON-RPC), habilitando retomada instantânea de threads, cache de servidores MCP, leitura nativa de cotas ([084](084.md)), plano vivo ([088](088.md)) e correção de rumo em andamento ([045](045.md)).

## Já existe

- `orchestrator/adapters/codex.rs` executa `codex exec --json --skip-git-repo-check -m <model> -s <sandbox> -C <dir> -c mcp_servers.vokia...` iniciando um processo novo a cada turno, sem `session_id` persistido e retornando `limits: None`.

## Comportamento

- **Ciclo de vida do `codex app-server` (`orchestrator/adapters/codex_app_server.rs`)**:
  - Sobe um processo `codex app-server` compartilhado para as threads do provedor Codex, falando JSON-RPC sobre stdio.
  - Suporta `thread/start`, `thread/resume` (usando o `thread_id` salvo no SQLite por `(projeto, agente)`), `thread/unsubscribe`, `thread/archive` (ao remover agente/encerrar projeto, liberando bloqueio de pasta no Windows), `turn/start`, `turn/interrupt`, `model/list` e `account/rateLimits/read`.
  - **Pool de sessões ociosas (`CodexIdleSessions`):**
    - Desinscreve (`thread/unsubscribe`) threads sem turno ativo após **5 minutos** de ociosidade (nunca descarrega se houver turno rodando, aprovação pendente, pergunta aberta ou terminal em background).
    - Mantém o processo `codex app-server` vivo por **30 minutos** após o último uso para preservar o cache de lista de ferramentas MCP em memória (evitando até 10 s de cold start por servidor MCP).
    - Encerra a árvore de processos com `taskkill /T` (Windows) ou process group `SIGTERM → SIGKILL` (Unix) no shutdown do app.
- **Economia de tokens no prompt do Codex**:
  - Desativa por padrão via `-c` recursos exclusivos do app externo que não existem no Vokia (`features.tool_suggest=false`, `features.recommended_plugins=false`), economizando ~1.000 tokens de entrada por requisição sem sobrescrever configurações explícitas de skills do usuário.
- **Eventos estruturados completos**:
  - Consome `turn/plan/updated` → alimenta [088](088.md).
  - Consome `account/rateLimits/read` e `account/rateLimits/updated` → alimenta [084](084.md) (incluindo `creditsAvailable` e `rateLimitResetCredits`).
  - Consome `commandExecution` (`commandActions`) e `tokenUsage.last` → alimenta [090](090.md), [091](091.md) e indicador de ocupação da janela de contexto.
  - Suporta *steering* nativo durante turno ativo ([045](045.md)).
- **Resiliência e fallback seguro**:
  - Se o `codex` instalado for antigo ou incompatível com `app-server`, reporta erro claro orientando atualização (ou permite fallback explícito para `CodexJsonl` via configuração do provedor em `providers.json`).
  - Trata `timed out waiting for state db backfill` com mensagem acionável em português e timeout inicial estendido.
  - Detecta binário incompleto sem `codex-code-mode-host` quando modelos code-mode (ex.: GPT-6) exigirem.

## Estados e transições

- `parado` → `iniciando` → `pronto` (aceita threads) → `ocioso (0–30 min)` → `encerrado`.
- Thread individual: `nova` → `ativa` → `ociosa (0–5 min)` → `descarregada (mantém thread_id)` → `retomada (thread/resume)`.

## Critérios de aceite

1. Dado dois turnos consecutivos no mesmo agente usando Codex, quando o segundo turno inicia, então reutiliza o `codex app-server` e retoma o `thread_id` via `thread/resume` sem cold start de processo nem perda de contexto.
2. Dado um agente Codex ocioso por 5 minutos sem aprovações nem terminais em background, quando o timer vence, então a thread recebe `thread/unsubscribe` mantendo o `thread_id` recuperável.
3. Dado uma exclusão de agente ou limpeza de worktree no Windows, quando a thread é encerrada, então envia `thread/archive` antes de apagar a pasta para não falhar por arquivo travado.
4. Dado um turno ativo no Codex, quando o app recebe `account/rateLimits/updated` ou `turn/plan/updated`, então as cotas ([084](084.md)) e o plano vivo ([088](088.md)) atualizam em tempo real.
5. Dado o usuário enviando uma correção durante um turno rodando no Codex em modo steer, quando a mensagem é enviada, então entra no turno ativo sem esperar o fim completo.
6. Dado o encerramento do Vokia, quando o app fecha, então nenhum processo órfão de `codex app-server` ou MCP permanece rodando.
